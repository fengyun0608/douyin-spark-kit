# 续火 · 商业化需求文档

> 独立 App，基于开源仓库 `douyin-spark-kit` 的技术，复用星语服务端。
> 版本：v0.1（需求定稿草案）
> 日期：2026-11-25

---

## 一、产品定义

**一句话**：帮抖音用户自动保持「聊天火花」不断的小工具。

**不是什么**：
- 不是社交产品，没有内容、没有 Feed
- 不是抖音第三方客户端，不浏览、不发朋友圈
- 不是群发营销工具（明确禁止，也是账号最大的封禁诱因）

**核心价值**：
```
用户痛点：火花断了心疼，每天要记得发一句，忘了就归零
解决方式：绑定一次，之后每天自动发一条，永不遗漏
```

## 二、目标用户

| 画像 | 规模判断 | 付费意愿 | 关键诉求 |
|---|---|---|---|
| 情侣 / 密友（火花 100+ 天） | 核心人群 | 高 | 不能断，断了要哄 |
| 学生党（火花几十天，多个好友） | 主力人群 | 中 | 免费能用就行 |
| 主播 / 小商家（维护粉丝火花） | 高价值人群 | 高 | 多好友、批量、稳定 |
| 泛用户（火花个位数） | 长尾 | 低 | 不太在意 |

**首批目标**：火花 ≥ 30 天的用户。他们的沉没成本高，最愿意为「不掉」付费。

## 四、账号体系与登录

### 4.1 两层登录，必须分清

```
第一层：续火账号（咱们的）
   手机号 + 验证码 / 密码    ← 用户说的"账号密码登录"
   作用：多设备同步、订阅、数据归属

第二层：抖音账号（扫码）
   扫一次二维码 → 服务端存 cookie
   作用：实际发消息的凭证
```

**不要做抖音密码登录**：
```
① 抖音密码登录要过人机验证 + 短信，成功率低
② 密码泄露风险，用户不敢给
③ 扫码一次能维持数月，体验更好
```

### 4.2 账号模型

```
User            续火账号
  ├ id, phone, passwordHash, nickname, createdAt
  ├ plan           free | pro | team
  ├ planExpireAt
  └ devices        设备列表（多端登录控制）

DouyinAccount   绑定的抖音号（一个 User 可绑多个，按套餐限制）
  ├ userId, uid, mySecUid, nickname, avatar
  ├ cookieEnc       AES 加密存储，不落明文
  ├ status          active | expired | risk
  └ lastCheckAt

Friend          好友
  ├ accountId, convId, secUid, uid, nickname, avatar
  ├ sparkDays, sparkLastAt, sparkDeadline, convSalt
  └ selected

Task            每日任务
  ├ accountId, hour, minute, jitter, maxPerDay
  ├ texts, enabled, lastRunDate, lastResult

SendLog         发送记录
  ├ accountId, friendId, text, ok, error, createdAt
```

### 4.3 安全要求

```
· cookie 必须 AES-256 加密后入库，密钥不落在代码里
· 接口返回永不包含完整 cookie（只返回长度 / 是否有效）
· 用户注销 → 立刻删 cookie 和好友数据
· 密码 bcrypt，登录失败 5 次锁 15 分钟
```

## 五、功能清单

### MVP（1 周，能上线收费的最小集）

```
□ 手机号注册 / 登录
□ 扫码绑定抖音（服务端出码 + 排队）
□ 自动拉好友，按火花天数排序
□ 勾选好友（支持搜索）
□ 写文案（一行一条，随机选）
□ 设时间（时:分 + 随机偏移）
□ 每天自动发，记录结果
□ 火花快到期提醒（Push）
```

### V1（+1 周，提升付费转化）

```
□ 预览并发送（手动触发一次，看效果）
□ 发送报告（今天发了谁、成功失败）
□ 多账号（Pro）
□ 预设文案模板（企业化 / 日常 / 节日）
□ 撤回（发错了能撤）
□ 火花排行榜（谁快断了排最前）
```

### V2（+2 周，拉开差距）

```
□ 智能文案（根据上次聊的内容生成）
□ 双向提醒（对方快断了也提醒你）
□ 多平台（QQ 火花 / 微信互动）
□ 团队版（主播管理多个粉丝）
```

```
┌─────────────────────────────────────┐
│  客户端  Flutter（Android / iOS）    │
│  扫码页、好友页、任务页、报告页        │
└──────────────┬──────────────────────┘
               │ HTTPS
┌──────────────▼──────────────────────┐
│  API 层  Go（复用星语 xingyu-go）     │
│  认证 / 好友 / 任务 / 日志            │
└──────┬───────────────────┬──────────┘
       │                   │
┌──────▼──────┐   ┌────────▼─────────┐
│ 扫码服务     │   │ 定时调度器        │
│ Node+Playwright│  │ Go ticker 60s    │
│ 出二维码     │   │ 按北京时区判定     │
└─────────────┘   └──────────────────┘
       │                   │
┌──────▼───────────────────▼──────────┐
│  MySQL  用户 / 抖音号 / 好友 / 日志   │
└─────────────────────────────────────┘
```

### 资源测算（按付费用户算）

```
单个扫码会话：Chromium 约 300-400 MB，一次 20 秒
  4G 内存服务器 ≈ 同时 3-4 个扫码（必须排队）

定时发送：纯 HTTP 请求，几乎不吃资源
  1000 个账号 × 每天 20 条 = 2 万次请求/天，峰值很轻
```

**结论**：**成本瓶颈在扫码，不在发送。** 所以：
```
· 扫码必须排队（已实现）
· 扫码是低频操作（绑定一次用几个月）
· 发送可以承载上千账号
```

## 十一、风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 抖音改接口 | 全线瘫痪 | 开源社区帮盯；关键路径做降级；保留 WebView 兜底方案 |
| 账号被风控 | 用户流失 + 口碑 | 限速、随机偏移、文案多样化；明确告知风险；被封给补偿 |
| cookie 泄露 | 严重 | 加密存储、最小权限、定期轮换 |
| 竞品抄袭 | 价格战 | 靠好友数据沉淀 + 文案库 + 体验拉开 |
| 应用商店下架 | 断流 | 自有下载渠道 + 网页版兜底 |
| 苹果审核 | iOS 上不了 | 先只做安卓，iOS 后置 |

**必须在 App 内明确告知**：本工具会代你发送消息，存在账号风险，请自行评估。

## 十三、待决策

1. **独立 App 还是星语的插件页？** 建议独立——品类不同，用户不会为了续火花装一个 AI 聊天 App
2. **iOS 做不做？** 建议先不做，IAP 抽成 + 审核风险
3. **免费额度给多少？** 太松不付费，太紧没人用，建议 10 好友 / 5 条
4. **要不要做「代发朋友圈」等扩展？** 建议不做，扩大风控面
5. **定价是否跟随竞品？** 先看市面同类（如有）再定
